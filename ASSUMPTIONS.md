# Assumptions

1. **No real ads.** Per the brief, only test traffic is used: Meta dashboard-sent test webhook events plus local simulated leads through the same broadcast path (see items 11–12 for why Testing-Tool submits can't fire webhooks here). No ad account, campaign, or spend exists; test leads (`ad_id` empty/zero) are expected and treated as first-class leads.
2. **Meta App in Development mode, with a documented platform limit.** Admin/tester tokens and the webhook handshake work without App Review (see items 10–11 for the delivery gate this imposes). Production would require `leads_retrieval` App Review + a published app.
3. **Single Page + single Form** for the demo. The backend stores `page_id`/`form_id` per lead, so multi-form works, but the Loom shows one form to stay under 5 minutes.
4. **Ephemeral storage.** Leads live in server memory (newest-first array, deduped by `leadgen_id`). Restart clears history — acceptable for a PoC; README notes the Postgres swap.
5. **Realtime via WebSocket (Socket.IO), not polling.** The app never polls; it renders `leads:init` on connect and `new-lead` pushes. Pull-to-refresh only re-fetches history as a safety net. This satisfies "without any manual action on the device".
6. **Lead enrichment needs a Page Access Token.** The webhook itself carries only `leadgen_id`; full name/email/phone require `GET /{leadgen_id}` with a token holding `leads_retrieval`. If the token is missing/expired the backend still broadcasts an ID-only card (clearly labelled) so the demo never stalls — full enrichment resumes once the token is set.
7. **Network.** Phone/simulator and laptop share a network (or ngrok for Meta → laptop). Expo Go on the same Wi-Fi, or emulators with `10.0.2.2`/`localhost` mapping, per `mobile/src/config.js`.
8. **One-screen app is intentional.** The brief asks for "the leads list screen already open" — a single focused screen demonstrates this best; no auth/navigation to distract from the realtime moment.
9. **Timestamps are server receipt time + Meta `created_time`** (both shown); timezones render in device locale.
10. **App stays in Development mode (unpublished).** Publishing is blocked: the Publish page requires completed business verification (documents + review queue, still pending — the Publish button is disabled). This is a platform gate, not a code limitation.
11. **Meta delivers only dashboard-sent test webhooks to unpublished apps.** No Page event delivery — not even for admins — until the app is published (Meta's stated policy). The Lead Ads Testing Tool does not operate in developer mode, so a Testing-Tool submit fires no webhook in this state. Verified: Page→App subscription (`leadgen`) exists and credentials are valid; the inspector simply never receives Meta traffic for Testing-Tool submits.
12. **Demo uses Meta-originated dashboard test events + local leads.** The Webhooks dashboard Test/Send-test-event button sends real POSTs from Meta's servers (visible in ngrok inspector with Facebook User-Agent) through the full path: `POST /webhook` → Graph lookup attempt → Socket.IO `new-lead` → live render. Enriched cards (name/email) are shown via `POST /api/test-lead`, which runs through the identical `saveAndBroadcast` path. The video discloses this on camera.
13. **Going Live was deliberately avoided.** Per Meta's docs, switching to Live before App Review deactivates unapproved permissions even for app admins — which would break `leads_retrieval` enrichment. The PoC keeps working admin-token enrichment by staying in Development.
14. **Dashboard sample IDs enrich gracefully.** Meta's sample `leadgen_id`s are not real leads, so Graph lookup fails and the backend broadcasts a clearly-labelled ID-only card (`meta-webhook-unenriched`) instead of stalling — by design (see `index.js` fallback branch, covered in Loom 2).
15. **VERIFY_TOKEN is a numeric string** (currently the form ID), matching the value entered in the Dashboard webhook subscription. Verification is plain string equality, so this works; a secret random token is recommended for production.
16. **Recorded on Android emulator**, so `mobile/app.json` sets `backendUrl` to `http://10.0.2.2:3001`. Other targets need their own URL (iOS sim: `localhost`, physical phone: laptop LAN IP) — see README table. `expo-constants` is pinned as a direct dependency (it is imported by `App.js`).
